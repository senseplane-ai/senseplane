# 56. One compose file for self-hosting, Caddy in front

Date: 2026-10-17 · Status: accepted

## Context

Running Senseplane on a server meant the development compose file, a secrets
script, a reverse proxy configured by hand, a console built separately and
a dozen public URLs set to match (`API_PUBLIC_URL`, `CAPTURE_URL`,
`MCP_PUBLIC_URL`, `MEDIA_URL`…), each as an environment variable. Anyone with
a fresh VM should instead install Docker, edit a few settings and run
`docker compose up -d`.

## Decision

- **`docker-compose.yml` at the repository root** runs the same services as
  everywhere else (postgres, valkey, s3, api, mcp, media, brain) plus Caddy.
  A settings block at the top (`x-settings`) is the only part people edit:
  the domain, an ACME contact, the model endpoint and key, optional model names
  and retention, and an optional announced address. Values are plain YAML, not
  `${VARIABLES}`; host ports alone can be moved in a `.env` file, for local
  testing.
- **One origin.** Caddy serves the console and proxies the API (`/v1`,
  `/auth`, `/playback`, `/media`, and `/api/` for the console's default base),
  MCP (`/mcp`, `/oauth`, `/.well-known`), WHIP (`/whip`) and signalling
  (`/signal/`) on the one domain, with automatic HTTPS (its own CA for
  `localhost` and IP addresses). Internal routes are not proxied. WebRTC goes
  to the media plane's RTC port directly, as before. The console image is
  Caddy plus the built console, the same for every domain: the console calls
  its own origin and learns the MCP address from the API.
- **A one-shot `init` service** (the api image, `dist/selfhost.js`) runs
  before the others on every `up`. It creates the instance's secrets once into
  a `secrets` volume and never rotates them (later versions only add missing
  ones), derives every public URL from the domain, resolves the domain to get
  the media plane's announced address, and writes one env file per service,
  owner-read only for that service's user. Services source their file and
  start as usual; a changed setting reaches them on the next `up -d`
  (`depends_on … restart: true`). Nothing prints a secret.
- **The first person to sign up owns the workspace**, then sign-up closes
  (`AUTH_SIGNUP=first`, serialised with an advisory lock). Invites still work.
- **Images:** every service names `ghcr.io/senseplane-ai/<service>:<release line>` (`:0.1`),
  so the file alone is enough. `docker-compose.build.yml` adds the `build:`
  sections for building from a clone.
- **Secrets people add** (the model key, optional GitHub/Google sign-in apps)
  go in the settings block; `init` hands each only to the service that uses it.

## Consequences

- Every deployment still runs the same services and routing; only the
  configuration source differs.
- Upgrading within a release line is `docker compose pull && docker compose up -d`;
  the edited settings block stays as it is.
- The development stack (`deploy/compose`) is unchanged for contributors.
- Real certificates and a real public address can only be checked on a VM
  with DNS; the local test uses `localhost` and Caddy's own CA.

## Addendum (2026-10-17): passwords in the settings block

The database, Valkey and object-storage passwords are in the settings block
too, with defaults to change before real use, and are applied on every start.
Signing and encryption keys are still generated by `init` and never shown.
