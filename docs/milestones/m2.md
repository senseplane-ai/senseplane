## Single-node load test (`media/load/run.ts`)
Apple M1 Max, 10 cores, 64 GB; 8 mediasoup workers; 1080p25 H.264 input
(2 Mbps target, 1.4 Mbps actual for the synthetic pattern); recording to the
local RustFS. The replay senders (load generator) ran on the same machine and
are excluded from the numbers.

| Streams | Duration | Media node CPU (avg / max, % of one core) | Media node RSS | Result |
|---|---|---|---|---|
| 5 | 45 s | 6 / 7 % | 0.4 GB | all recorded |
| 50 | 180 s | 33 / 48 % | 1.7 GB | all 50 recorded ≥ 179.6 s of 180; 1,576 segments |
| 100 | 90 s | 56 / 73 % | 3.1 GB | all 100 recorded; 1,844 segments |

Recording is a remux, so CPU is low; memory (~30 MB per FFmpeg recorder) and
object-store bandwidth are the limits. 50 × 1080p fits comfortably on one node.

## Built
- Signed HLS playback (ADR 0018), gap-aware timeline API, clips copied to
  `clips/…`, and the retention sweeper (ADR 0016; per-account and per-source
  `retention_days`, objects then index rows, advisory lock for one sweeper).
- Console: Playback screen (24 h timeline with gaps, last minute / 5 min / hour,
  player, save as clip), Clips list (play, delete), and `play.html` for a bare
  signed URL.
- SDK: `sources.timeline`, `clips.get`.

## Long run and a memory leak

**The first long run showed a leak, now fixed.** Over 84.8 min (848 segments,
still 0 gaps) the media container grew 74 → 118 MiB: the Node process 120 →
141 MB RSS and the recorder FFmpeg 17.8 → 20.9 MB. Two causes in the
`segments` egress:

1. The 500 ms upload poll chained a promise per tick. When a collect pass was
   slower than the interval (under load), the chain grew without bound.
   Reproduced in an accelerated test (`media/load/leak.ts`: 20 sources,
   1 s segments): V8 heap 32 → 75 MB in 8 min.
2. The recorder's HLS playlist kept every segment (`hls_list_size 0`), so
   FFmpeg's memory and each parse of the playlist grew for the life of the
   recording.

Fixes: one collect at a time (ticks are skipped, not queued) and a rolling
20-entry playlist. The same accelerated test then held the heap flat at
27–28 MB for 10 min (20 sources, analysis feed on).

**On the fixed build**, a run with one replayed source was stable for about
17 h: segments kept coming with no gaps over 1 s and the media container's
memory stayed flat at 67–85 MiB. The host then failed for reasons unrelated
to Senseplane, which ended the run, so a full 24 h result is still to be
recorded.
